Scaling ai_classify from a 2.2M POC to 600M rows

A requirements and best-practices spec for running large-scale AI-based text classification on Databricks — how to prove it at POC scale, extrapolate honestly, and execute the full backfill without surprises on cost, throughput, or reliability.

POC 2.2M rows Target 600M rows Function ai_classify v2.1 Pricing compute-based (MU-hours) Engine DBSQL / Serverless
00

The one thing to internalize first

Every decision in this document follows from a single fact: AI Functions batch inference is priced on compute, not tokens. When you submit a batch, Databricks provisions GPU capacity — measured in Model Units (MU) — processes the job, and scales down. You pay for MU-hours allocated over the job's duration, not for input/output tokens.

Cost=Model Units provisioned×price / MU-hour×job duration

Consequence 1 — no universal $/row

There is no reliable rows-per-minute or cost-per-row figure to look up. Compute-based cost depends on your data and output size. You must benchmark to get real numbers.

Consequence 2 — faster ≈ same cost

Raising the MU ceiling shortens wall-clock time at roughly the same total cost, because you consume similar MU-hours in less time at higher parallelism.

Consequence 3 — output tokens are the lever

Duration scales with total work — dominated by output tokens. Rationales and confidence text inflate output and are the #1 cause of blown estimates.

Consequence 4 — do less work

The cheapest classification is the one you don't run. At 600M rows, deduplication is the dominant cost lever — classify distinct text, join labels back.

Diagnostic that matters most

Check the run's billing / query metadata. COMPUTE_TIME means you are on the batch / AI Functions path (capacity-based — the guidance here applies). TOKEN means you slipped onto the PPT / FMAPI path (token-based) — a slow TOKEN run is a capacity investigation, not warehouse tuning. Do not stand up a customer-managed Provisioned Throughput endpoint first: AI Functions does not run on PT-endpoint compute.

01

Hard requirements

Baseline conditions the job must satisfy before it can run at scale. Must blocks execution or correctness; Should is strongly recommended; Avoid is a known anti-pattern.

REQ-01
Must

Runtime & engine floor

Use DBR 16.1+ for AI Functions (never below 15.4 LTS). Runs on Serverless / SQL Warehouse — not SQL Classic. ai_classify cannot be applied through a View.

REQ-02
Must

Use ai_classify v2.1 explicitly

Pin version = '2.1' in the options map. v2.1 returns a VARIANT — {response:[{value, confidence_score}], metadata, error_message} — which differs from v2.0 (plain strings) and v1.0 (single string). Downstream parsing must read .response[*].value.

REQ-03
Must

Stay within the label ceiling

2–500 labels in v2.x, each 1–100 chars, content ≤ 1M tokens. If the VOC taxonomy exceeds ~500 categories, ai_classify is the wrong tool — switch that portion to vector_search + LLM.

REQ-04
Must

Deduplicate before classifying

At 600M rows this is not an optimization, it is the architecture. Classify the distinct normalized text set, then join labels back to all rows. See §03.

REQ-05
Must

Checkpoint the full backfill

600M rows cannot ride on a single non-resumable query. Use Structured Streaming with trigger(availableNow=True) + a checkpoint location so a failure at row 400M resumes instead of re-running (and re-paying) from zero.

REQ-06
Should

Turn rationales off in production

Keep enableRationales (and often enableConfidenceScores) on for QA only. In the prod path they inflate output tokens → longer duration → more MU-hours, for output you won't store.

REQ-07
Should

Prefer the managed model; benchmark before switching

Task-specific ai_classify uses a Databricks-managed model (no model choice) — this is the intended path. Only if model selection is mandatory, move to ai_query and test gpt-oss-120b first, then llama-4-maverick. Do not promise Sonnet-equivalent quality without a representative eval.

REQ-08
Avoid

Manual micro-batching & parallel notebooks

Do not split the work into small chunks or fan out across notebooks. It shows up as a spiky MU-utilization graph and reduces throughput. Submit one large set-based query and let the platform parallelize.

REQ-09
Info

Governance & compliance are covered

Data stays in your workspace/region, is never used for training, transient logs only. HIPAA on all clouds; PCI/FedRAMP via Compliance Security Profile. UC lineage/audit apply. Pin the output schema version for compliance stability.

02

The dedup lever — why 600M is really far fewer

Voice-of-customer text is highly repetitive: canned responses, short common phrases, template fragments. You are billed for work done, so classifying 600M rows when only a fraction are unique is paying many times over for the same answer. Measure the distinct ratio on the 2.2M POC, then classify only distinct normalized text and join labels back.

Illustrative leverage at 600M — replace ratio with your POC-measured value
Distinct ratio (measured)Distinct rows to classifyWork vs. naïveImplication
10% (very repetitive)60,000,00010× lessDedup alone is the difference between feasible and not
25%150,000,0004× lessLarge saving; still needs streaming + MU increase
50%300,000,0002× lessWorthwhile; verify normalization is aggressive enough
90% (near-unique)540,000,0001.1× lessLittle help — expect full-scale cost, plan capacity accordingly

Normalization quality drives the ratio: lower-case, trim, collapse whitespace, and consider stripping punctuation/IDs before the DISTINCT. Match your normalization on both sides of the join.

-- 1) Classify only DISTINCT normalized text — the dominant cost lever at 600M
CREATE OR REPLACE TABLE voc.distinct_labeled AS
SELECT
  text_norm,
  ai_classify(
    text_norm,
    labels,                                  -- array, or {label: description} map
    map('version','2.1', 'multilabel','true')   -- rationales OFF in prod
  ) AS classification
FROM (SELECT DISTINCT lower(trim(text)) AS text_norm FROM voc.raw_600m);

-- 2) Join labels back to all 600M rows (cheap — no inference here)
CREATE OR REPLACE TABLE voc.labeled AS
SELECT r.*, d.classification
FROM voc.raw_600m r
JOIN voc.distinct_labeled d ON lower(trim(r.text)) = d.text_norm;
03

The staged path from POC to 600M

Do not extrapolate from a 100-row test — the system needs volume to reach steady-state throughput, so small tests always feel slow. Move through four gates, and only pass each when its exit criteria are met.

Stage 0 · Calibrate

Micro-benchmark

50K–100K distinct rows
  • Confirm labels, descriptions, and prompt/instructions
  • Rationales ON — inspect quality of a sample
  • Record avg output tokens per row
  • Confirm metadata shows COMPUTE_TIME
Exit when labels & output shape are locked and token size is known.
Stage 1 · Prove

Run the POC

2.2M rows
  • Measure the distinct ratio (§02)
  • Rationales OFF (prod config); QA sample separately
  • Capture MU-hours, duration, success rate from go/batchinference/debug
  • Quality eval on a labeled sample
Exit when quality passes and per-distinct-row MU-hours is measured.
Stage 2 · Project

Extrapolate & size

math, not compute
  • Compute 600M distinct set = 600M × ratio
  • Estimate MU-hours & cost (§04)
  • Decide MU ceiling for target duration
  • File go/batchlimitincrease if needed
Exit when cost/duration are approved and capacity is granted.
Stage 3 · Execute

Full backfill

600M rows
  • Structured Streaming + checkpoint (resume-safe)
  • failOnError => false; monitor MU graph live
  • Then run incrementally for new data
  • Verify billing under AI_FUNCTIONS
Exit when all rows labeled at ≥95% success and cost matches projection.
Throughput reality

ai_classify needs roughly 25K–50K+ rows to reach steady-state throughput; the first few minutes are ramp-up. At 600M you are far past that floor — the risk is not "too small to be fast," it is the MU ceiling and output-token size. Benchmark at 50K–100K, never at 100 rows.

04

Estimating cost & sizing capacity

Because cost is compute-based, the only honest estimate comes from measuring at POC scale and scaling by the distinct row count. The method:

  • From Stage 1, read MU-hours consumed and distinct rows processed (Dpoc) off the debug dashboard.
  • Per-row rate = MU-hourspoc ÷ Dpoc. This is the number that travels.
  • Target distinct set Dprod = 600M × measured distinct ratio.
  • Estimated MU-hoursprod ≈ per-row rate × Dprod (roughly linear in total work).
  • Estimated cost ≈ MU-hoursprod × price per MU-hour.
  • Estimated duration ≈ MU-hoursprod ÷ MU ceiling — so raising the ceiling shortens the run at ~constant cost.
The estimate-buster

Linear scaling only holds if output tokens per row are stable. If rationales were on during the POC but off in prod (or vice-versa), the per-row rate is wrong. Lock the exact prod configuration before the Stage-1 measurement.

05

The execution pattern for the backfill

For the 600M run, wrap the distinct-set classification in Structured Streaming so it checkpoints. The payoff is resume-on-failure: a crash at row 400M of the distinct set restarts there, not at zero.

# Structured Streaming with AI Functions — resume-safe backfill
from pyspark.sql import functions as F

stream = spark.readStream.table("voc.distinct_text")   # DISTINCT normalized text

labeled = stream.selectExpr(
    "*",
    """ai_classify(text_norm, labels,
                   map('version','2.1','multilabel','true')) AS classification"""
)

(labeled.writeStream
    .trigger(availableNow=True)                     # process all available, then stop
    .option("checkpointLocation", "/Volumes/voc/_chk/classify")
    .toTable("voc.distinct_labeled"))

# If it fails partway, just re-run — the checkpoint skips finished rows.
Steady-state hygiene

Keep everything at DataFrame / set level (never row-by-row loops). Use failOnError => false so a few bad rows don't kill a multi-hour job — inspect the error column afterward. Batch is optimized for volume: one big stream beats many small triggers.
